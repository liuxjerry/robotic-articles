# Same Model, 65.7% to 97%. A Real-Robot Benchmark Just Got Retired.

For the past few months, I’ve been keeping a list on GitHub.

It follows one question I care a lot about: how well frontier models like GPT, Claude, and Gemini can control real robots, and whether they’ll eventually push aside the robot models that companies train specifically for the job.

Every morning, an agent goes through new papers, lab blogs, and leaderboards and updates the list for me. I check its work and step in when something looks off.

One of the tables I watch most closely is RoboDojo-RC Tier 1. Until a few days ago, GPT-6.2 Astra sat there at 65.7%.

Today, Robocurve, the team that runs that leaderboard, posted a new score for the same model.

97%.

In the same post, they added one more line: “We are retiring RoboDojo from future evaluations.”

My first reaction was that something had to be wrong.

A jump of more than 30 points, on real robots, with no new model. In AI, a jump that size almost always comes with a new release. This time there wasn’t one.

So I spent the afternoon reading everything Robocurve has published about it. By the end, I was convinced the number holds up. I also think it says something important about where model-driven robots are right now.

Let me walk you through it.

First, some background on the benchmark, or the numbers won’t mean much.

RoboDojo is a robot manipulation benchmark that came out this July. It has simulated tasks, real-world tasks, and a public leaderboard where teams submit their robot policies.

Robocurve took six of the real-world tasks and rebuilt them on its own setup: a pair of YAM arms from I2RT, working side by side over a tabletop. It calls this version RoboDojo-RC Tier 1.

Every system gets 20 attempts per task, 120 attempts in total. After each attempt, someone puts the objects back by hand. A human grader then scores how far the robot got, using a rubric for each task, so partial progress counts. The final number is the average across all 120 attempts.

The interesting part is who’s on the leaderboard.

There are frontier chat models: GPT, Claude, Gemini. There are robot models trained on large amounts of robot data, the kind the field calls VLAs (vision-language-action models), along with a newer type called world action models. And there are full agent systems that combine the two.

All of them run on the same robot and get scored by the same team.

That’s rare. Most comparisons between large models and robot models come from papers where each side uses its own setup, so the numbers rarely line up.

Real-robot testing is also slow and expensive. Every one of those 120 attempts needs someone to reset the table and grade the result by hand, for every system on the list. Most teams can’t afford to do that for anyone’s model but their own. Robocurve does it for all of them, which is why I check this leaderboard more often than almost any other.

Before this week, the top of the leaderboard looked like this.

Waddle-1 was first at 81.4%. It’s an agent system from Waddle Labs in which cloud LLMs direct lower-level policies that run on the robot itself. It also ran with no cap on model calls, so its setup differs from the single models below it.

GPT-6.2 Astra was second at 65.7%.

Dream-1, a world action model from Dream Labs, was third at 59.5%.

Claude Fable 5.2 came in at 57.5%, and Gemini 4 Carbon at 54.5%.

Further down, the open robot models MolmoAct2 and GR00T N1.7 scored 19.5% and 9.5%.

So frontier chat models were already scoring above most dedicated robot models on these six tasks.

How does a chat model control a robot arm in the first place?

Robocurve built an open-source harness for it called Inspect Robots. The model sees the scene through three cameras, one above the table and one on each wrist, and it also gets the robot’s joint state. It moves the arms through a tool called move_to, which takes a target position and sends the arm there.

Each model gets 40 calls per attempt. On every call, it looks at the images, thinks, and decides on a move.

Keep that detail in mind. It turns out to matter a lot.

Now for the new result.

Robocurve ran GPT-6.2 Astra through all 120 attempts again. This time, the model ran inside Codex, OpenAI’s coding agent.

It scored 97%.

Robocurve called it “the highest among anything we’ve tested.” That includes Waddle-1, every robot model, and every other frontier model on the leaderboard.

The hardest task in the set is capping a pen. One arm holds the pen, the other holds the cap, and the two have to line up precisely before the cap can go on. A small error in position is enough to make it fail.

Codex succeeded in 60% of its 20 attempts.

That’s double the runner-up, Gemini 4 Neon running in Google’s Antigravity.

None of the robot models Robocurve has tested managed to cap the pen even once.

Then came the line about retiring RoboDojo.

The first thing I checked was whether this really was the same model.

It was. Same GPT-6.2 Astra, same robot, same six tasks, same team doing the grading.

What changed was everything between the model and the robot.

People call that layer the harness: the tools a model can call, how often it can call them, and the loop that feeds results back to it. For a robot, the harness decides what a single decision by the model can make the arm do.

Robocurve wrote a detailed post comparing the two harnesses.

Here’s the link: https://robocurve.org/blog/codex-vs-inspect-robots/

On paper, the differences look like this.

Inspect Robots gives the model one fixed tool, move_to. It moves the arm in a straight line at a fixed speed and sends commands to the robot 10 times a second. The model makes one move per turn.

Codex works differently. It’s a coding agent, so when Robocurve handed it the robot, it wrote its own tools. The main ones are go, which moves the arm, and grip, which opens and closes the gripper.

go drops the straight-line requirement. It can slow down at the start and end of a motion, takes a speed setting, refuses targets the arm can’t reach, and sends commands 40 times a second.

Looking at that list, my first guess was that Codex had simply written better tools. Faster updates, smoother motion, speed control. It reads like an upgrade across the board.

Robocurve tested that guess. In a perfect simulation, they checked whether the old move_to could reproduce the motions Codex was making with go.

For the most part, it could. Their verdict on the idea that Codex’s tools are more expressive: “mostly wrong.”

So the answer had to be somewhere else.

The difference Robocurve calls “extremely consequential” looks small at first glance. Codex can send more than one go in a single turn.

Here’s why that matters so much.

Under Inspect Robots, every move costs a full model call. The model looks at the cameras, thinks for a while, sends one move, waits for the arm to finish, and then looks again.

Setting a fallen bottle upright takes a string of moves. Move above the bottle, lower down, close the gripper, lift, rotate, set it down, open the gripper. Each one is its own round of looking and thinking. With two arms, the count goes up again.

With only 40 calls, a task that needs a few careful corrections runs out of calls before it’s finished.

Codex can plan a short sequence and send it all at once: approach, lower, grip, lift. Then it checks the result and plans the next sequence.

Same model, same reasoning. Each time it thinks, it simply gets to act on more of what it has already worked out.

At this point, it’s still just a hypothesis. What convinced me was the experiment Robocurve ran next.

They picked one task, Stand Up Bottles, where the robot has to set three bottles upright. Then they changed one thing at a time and watched the score.

First, the original Inspect Robots with 40 calls.

Mean score: 0.48. All three bottles ended up standing in 4 of 20 attempts.

Second, the same harness, with the call limit raised from 40 to 200. If the only problem was running out of calls, this should have fixed it.

The score rose to 0.745. All three bottles stood in 5 of 10 attempts.

Now look at what that took. The model used a median of 173 calls. The median attempt ran 16.6 minutes. The average cost per attempt was $164.34.

That’s a lot of money for one robot to stand up three bottles. And it still failed half the time.

Third, they kept the 200-call limit and gave Inspect Robots the tools Codex had written, plus a way to send several moves in one turn. Robocurve calls this version IR+.

Score: 1.00. All three bottles stood in 10 of 10 attempts.

The median attempt used 30 calls and took 4.0 minutes. The average cost was $12.72.

For comparison, here’s Codex itself on the same task: 1.00, 20 of 20, a median of 54 calls and 3.8 minutes, and $7.05 per attempt.

Put the four runs next to each other and the picture is pretty clear.

Giving the model more calls helped a little and made each attempt almost 14 times as expensive.

Giving the old harness Codex’s tools and multi-move turns closed the whole gap, with fewer calls than the original 40.

That’s why I trust the 97%.

It’s the same model, measured by the same team, and the experiment changes one variable at a time until the scores match. And the team that ran it also built the harness that lost. They had every reason to want Inspect Robots to look good, and they published the comparison anyway.

Robocurve’s own conclusion is careful. Of the explanations they considered, the one they think is most likely is that the model does better when it writes its own tools. They suspect multiple moves per turn is the main driver, and they still call the key component “an open question.”

I also want to be straightforward about the limits, because they’re real.

First, the authors themselves say it’s “somewhat mysterious” why Codex does better. They describe how Codex’s tools behave “to our understanding,” and they checked the move_to replication only in a perfect simulation. They also set aside other differences between the two harnesses for now, such as the system prompt and how each one manages context.

Second, the graders knew which system was running. Robocurve says openly that the grading “is open to unconscious bias.”

Third, Tier 1 is the easy tier. Robocurve picked these six tasks because they were the ones where GPT-6 Astra had scored highest. A 97% here tells you a lot about these six tasks and much less about what a robot can do in a messy kitchen.

Fourth, cost.

Each attempt with Astra on Codex cost $9.46. Dream-1 cost $0.15. In Robocurve’s words, robot models are “63x cheaper.”

Two details are worth adding. Astra was running at its Ultrafast tier, which currently costs three times the standard rate. And under the old harness, the same Astra cost $10.51 per attempt to reach 65.7%. So moving to Codex raised the score and slightly lowered the cost. Next to Dream-1, though, it’s still in a completely different price range.

Speed is harder to pin down. Robocurve didn’t publish Codex’s time per attempt for the full 120 runs. On the bottles task, the median was 3.8 minutes. Dream-1 averaged 1.5 minutes per attempt across all six tasks. The two numbers come from different measurements, so treat them as a rough sense of scale.

Back to the retirement.

Robocurve didn’t explain the decision in its post. Here’s how I read it.

A benchmark stays useful as long as it can separate one system from another. With the top score at 97%, there are three points of room left. And when the jump to 97% came from changing the harness with the model held fixed, the top of the leaderboard is mostly measuring harnesses. It can’t tell you much more about the models.

That’s what saturation looks like. Every good benchmark gets there eventually, and the sensible thing to do is retire it and build a harder one.

I’d like the next generation of real-robot benchmarks to do two things.

One, use harder tasks. Fine alignment like the pen cap, soft and deformable objects, longer sequences, cluttered scenes.

Two, report the harness, the cost, and the time next to every score. “GPT-6.2 Astra: 65.7%” and “GPT-6.2 Astra: 97%” are both accurate. Without the harness written next to them, you can’t make sense of either one.

So what do I take away from all this?

The first thing is about how I’ll read leaderboards from now on.

“Which model is best at controlling robots?” is only half a question. The full question is which model, through which harness, with how many calls, at what cost.

I’d seen hints of this before. On the simulated version of RoboDojo, the JustRUA team ran GPT-6 Astra through a leaner harness of their own and scored 50.3, against 29.7 with the official harness. CaP-X, a benchmark from Berkeley, NVIDIA, and others, found that giving coding agents more rounds of execution and feedback recovers much of what they lose when you take away hand-built tools.

Those results came from simulation, or from papers where the authors ran both sides themselves. This is the first time I’ve seen it on real robots, with the same model, scored by an outside team that built the harness that lost.

That’s why I added it to the Milestones table in my list.

Here’s the link: https://github.com/liuxjerry/awesome-frontier-models-as-robot-policies

I keep that table strict. An item has to be a real turning point, the evidence has to compare like with like, and it has to fit in one sentence that anyone can check against the source. This one passed easily. The top real-world score on RoboDojo-RC came from swapping the harness while keeping the model, and the same GPT-6.2 Astra had scored 65.7% under the benchmark’s own harness.

The second thing is about the question my list is built around. Will frontier models replace the robot models built specifically for control, what the field calls a robot’s System 1?

On these six tasks, a frontier model with a good harness now beats every robot model Robocurve has tested, and by a wide margin on the hardest task.

It also costs 63 times as much per attempt, and the time figures that do exist suggest it’s slower too. A robot in a factory or a home runs thousands of attempts a day, and at that scale, cost and speed carry a lot of weight.

So here’s where I’ve landed for now.

Frontier models are winning the tasks where there’s time to think, and they’re getting there faster than I expected. Cheap, fast learned policies are still the practical choice for work that has to run all day. And systems like Waddle-1, which put an LLM in charge of local policies, are an attempt to get the best of both.

One last thought.

Until this week, GPT-6.2 Astra sat on that leaderboard at 65.7%.

Same weights, same cameras, same arms.

All that held it back was that it could move only once each time it looked.

Let it act on a few steps at a time, and it caps a pen that no robot model on the leaderboard ever managed.

It makes me wonder how many of the scores in my list are measuring the harness more than the model.

I’ll be watching for the next benchmark Robocurve builds.
